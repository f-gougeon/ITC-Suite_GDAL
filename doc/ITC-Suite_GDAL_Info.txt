Introduction:

	For more details on how to run the ITC-Suite, please check the ITC-Suite Manual from 2010:

	Gougeon, F.A. 2010. The ITC Suite Manual : A Semi-Automatic Individual Tree Crown (ITC) Approach 
	to Forest Inventories. Natural Resources Canada, Canadian Forest Service, Pacific Forestry Centre,
 	Victoria, B.C. Canada. June 2010. 92  p. 
	http://cfs.nrcan.gc.ca/publications/?id=31918

	The ITC-Suite, first developed for the ARIES image analysis system in the 90's,
	mostly ran under PCI/XPACE, then PCI/EASI, with PCI/ImageWorks and later PCI/Geomatica 
	to display and deal with PCI's ".pix" files (PCI v2010-2022 at this time)

	Instead of a PCI file containning all, it is now assumed that all will be in 
	a single "project directory": images as tif files, bitmap as 1-bit tif files, 
	vector layers as shp files, signatures as discrete files, etc., and
	that ArcGIS (or other software) may be used to view all these.

	In order to deal with less items on the command line, file nomenclature is
	often predefined, but often using a "base file name" from the main image file.

	Having an image file name such as "BaseName_IRGB.tif" for example
	will ensure that other files will be of the type "BaseName_aaaa.ext"
	For examples, "BaseName_VFOL.tif"   as output from itcvfol_g.exe
	or "BaseName_ISOL.tif"  as output from itcisol_g.exe
	Of course the "BaseName" should reflects the name of the main project in that directory.
	The underscore is use to separate the "base file name" from the rest of the file name.
	Full directory path is now mostly supported (i.e., not fully tested yet as the philosophy 
	was to do everything in the same directory from a "cmd windows"). However, it was needed
	for the integration of the GDAL version of the Suite used with a ArcGIS Toolbox (GUI).

	The GDAL version of the ITC-Suite can be used from ArcGIS or ArcGISPro via appropriate
	toolboxes, allowing users to stay completely with that environment.


	NOTE:	Partial use of a PCI file is often possible (as input). However,
		user entered segment numbers will be that of GDAL, not of PCI.
		Use "gdalinfo" and "ogrinfo" on the PCI file to find that order.
		(e.g., bitmaps are numbered after images, vector layers are separate,
		signature segments are not visible, ...)

	NOTE:   The "ITC-Suite Manual" and "ITC-Suite.chm" are still very relevant to all this 
		but should be used as guides, not gospel.

	NOTE:	My GDAL programs always complain when overwriting an exiting output file.
		Most of the time, it is not an issue. However, sometimes when PCI/ArcGIS has control 
		of the file, it may not overwrite at all and leave you with previous results

	NOTE:	Most of the output files produced will carry a description of their
		immediate provenance. Use "gdalinfo" to see that OR to only see 
		the description, use for example:
		> gdalinfo  PP1493386_Lengths_BM.tif | grep -i Description	OR
 		> gdalinfo  PP1493386_Lengths_BM.tif | findstr Description

This document describe the "GDAL ITC-Suite programs" and their parameters as used
from a "cmd window" (under the Windows operating system) or from a "terminal window"
under a Linux operating system.

However, they can be used from a convenient GUI under ArcGISPro (from a ToolBox).
Here, we will give the examples for ArcGISPro and GDAL v3.10

The "ITC-Suite-GDAL-v3-10.tbx" toolbox shows a list of the "main" ITC-Suite programs.
Clicking any of them will allow you to enter its parameters and run the program.

*Before running* a program, one needs to run a script (once) that will setup the
environment for the GDAL ITC-Suite and for GDAL, for example:  "GDAL_Setup_V3_10"
that should be in that toolbox.

This will call a Python program (GDAL_V3_10_Setup.py) that will do the setups.
You may need to modify that program (within Arc or as a text file) if the locations
of the GDAL ITC-Suite or GDAL itself (and geo-projections) are different on your PC.


NOTES: 	Some utility programs are not available in the ArcGIS toolbox and thus,
	only available from the "command prompt" window interface.

	GDAL "perse" has a lot of interesting programs that also available:
	gdalinfo, ogrinfo, gdal_translate, ...

C	ITCMG.cpp    (ITC Mask Generator)
c
c 	ITC Mask Generator - Generates LIT/SHADED/TT masks
C
C	This is a program for the PCI EASI/PACE Image Analysis System that takes the
C	bitmap generated by ITCISOL and the same illumination channel to generate a bitmap
C	assumed representative of the lit side, shaded side, or top of tree crowns (i.e., MAX).  
c	This bitmap may be used as "extra bitmap" mask (EXTBIT) in ITCSSG and ITCSC
c	to create signatures and classify trees using only that "purer" part of the crown.
c
c	Optionally (for research purposes), the bitmap of automatically delineated 
c	crowns (ISOLBIT) can be replaced by a vector layer of manually delineated crowns.
C
c**************************
c
c	PROGRAM USAGE EXAMPLE
c
c	Using PCI Variable Notation:
c
c	> itcmg_g   ILLUMCH  ISOLBIT  MASKTYPE
c
c
c	> itcmg_g SECTEUR_CH5.tif SECTEUR_ISOL.tif LIT	(most typical)
c
c	Program will create "SECTEUR_MG.tif" that you can rename later
c
c	IF some input files are PCI files OR other multi-feature files
c	an additional question will be asked about channel or bitmap 
c	number to use (in GDAL, bitmap numbers are sequential # after last 
c	channel number, if 5 channel, first bitmap is Ch6; and vector layers
c	are independent, starting at 1)
c	Please use "gdalinfo" and "ogrinfo" on files to find out numbering scheme)
c
c	Usage with manual trees and other notations:
c
c	> itcmg_g SECTEUR_CH5.tif SECTEUR_VEC2.shp LIT

c	> itcmg_g SECTEUR.pix,5 SECTEUR_VEC2.shp LIT

c	> itcmg_g SECTEUR.pix SECTEUR.pix LIT	
	NOTE: 2nd file will ask which bitmap or vector layer to use
c
c	> itcmg_g SECTEUR.pix,5 SECTEUR.pix,2 LIT	
	NOTE:	Will use CH5 and segment 2 (bitmap or vector, here vector)

	Program name: 	itcssg_g.cpp (for GDAL)
	Author: 	Francois A. Gougeon
	Date:		March 2020 - Nov. 2024

	ITCSSG generates ITC-based signatures for different species of trees.

	For a set of channels, it typically uses an ITC bitmap generated by 
	ITCVFOL&ITCISOL and a series of training bitmaps (TRAINSEG, areas for 
	plantations and uniform stands, OR screen selected ITCs (using DCPE) 
	for mixed forests) to generate ITC-based signatures for different 
	species (class) of trees.

	Based on masks formed by ~ANDing the ITC bitmap and training bitmaps,
	regions of the image are scanned for tree crowns and a signature is
	calculated for each "species" (class) based on the MSS data under the
	crowns in that region of the image. Crowns spanning the boundary of a
	training area are included/excluded based on the BITBOUND parameter.
	Various signature types (MEAN/TCL/TCL2/TEXTUR/STRUCT) or combination
	of signature types (MEAN+TEXTURE) are available. 

	An optional EXTBIT mask can further specify which part of each tree crown  
	(LIT/SHADE/TT) should be processed instead of the full crown.  

	The signatures are written to the output segments specified by SIGNSEG. 
	If SIGNSEG is empty than new signature segments are generated.
 
	Optionnally, if a SDBOUT filename is specified, the signature of each ITC
	and the species signature are also written to a text file (potentionnally,
	for detailed analysis or plotting (e.g., SAS, Splus, Exel, ArcGIS, ...).

	Species signatures can also be generated from manually delineated tree 
	crowns (in bitmaps or vector layers) using the TREETYPE = ManBM or 
	ManVec, respectively. In these modes, as in previous modes (ITC/TT),
	a bitmap or a layer segment (TRAINSEG) is required for each signature 
	to be generated and the number of signatures to be generated is governed
	by the number of elements in TRAINSEG.

	NOTE:	Manually delineated crowns in bitmap form shall not touch each
		other (at least, not 4-connected). Manually delineated crowns 
		in vector form do not have this limitation.

	An other mode of operation also exist (SLayer) when all polygons manual tree
	crowns are in a single vector layer (ISOLBIT) and a field (TRAINF) labels
	the class that each tree belongs to. Since the field pointed to by TRAINF
	can contain other information or refer to classes that are not of interest
	for the current run of ITCSSG, the parameter CLASCODE is used to select
	the classes of interest. The number of elements in CLASCODE will thus 
	govern the number of signatures segments to be generated.

	TRAINF, the field specifying the training class for the manuallly delineated
	vector tree crown in single layer mode (SLayer) can be specified in advance.
	For example,
			TRAINF = "train_class
			run ITCSSG
	This facilitates automatic (unattended) runs via EASI scripts.
	If TRAINF is left unspecified, the user will be prompted for a field name.



		PARAMETERS
		


	ITCSSG is controlled by the following global parameters:

	Name		Prompt								Count Type

	FILE		PCI Database File Name				132	Char
	DBIC		Database Input Channel List			8	Int
	ISOLBIT		ITC Bitmap from ITCISOL				1	Int
 	TRAINSEG	Training Segments (BM/Vect)			16	Int
	DBIW		Database Input Window				4	Int
	SIGNSEG		Signature Output Segment List			16	Int
	CLASCODE	Class code (used in SLayer mode)		16	Int
	SIGTYPE		MEAN/TCL/TCL2/TEXTUR/STRUCT			64	Char
	TREETYPE    ITC/TT/ManBM/ManVec/SLayer         	 		64  Char
	EXTBIT		External Bitmap Mask				1	Int
	BITBOUND	Boundary ITCs:INC/EXC/AUTO/CGRAV/POINTS		64	Char
	SDBOUT		Signature Database Filename			132	Char
	REPORT		Report Mode: TERM/OFF/filename			132	Char


		FILE
		

	Specifies the name of the PCI file containing the input images
	and bitmaps and/or vectors, and that will receive the output
	species signatures.

	EASI>FILE="filename"

		DBIC
		

	Specifies the input database channel(s) holding the input MSS image.
	A list of up to 8 channels may be specified.

	EASI>DBIC=n,n,n...

		ISOLBIT
		

	Typically specifies a bitmap of individual tree crowns (ITCs) 
	produced by the ITCISOL program.

	EASI>ISOLBIT=n

	Based on masks formed by ANDing this ITC bitmap and training bitmaps,
	regions of the image are scanned for tree crowns (min. 2x2 pixels)
	and a signature is calculated for each "species" (class) based on 
	the MSS data under the crowns in that region of the image. 
	If ITCs are to be used in TRAINSEG (rather than training areas), the
	ITCs should preferably have been generated by using DCPE, 
	and thus be exactly the same as the equivalent crown in ISOLBIT.

	If as specified by (TREETYPE=ManBM or ManVec) and in the TRAINSEG,
	manually delineated tree crowns (bitmaps or vectors, respectively)
	are to be used as prototypes for each species, the ISOLBIT is 
	disregarded.

	In single input layer mode (TREETYPE=SLayer), ISOLBIT is used to
	specify the layer of training manually delineated tree crowns from
	which to generate the signatures. CLASCODE specifies with signatures
	will actually be generated.
		

	PHILOSOPHIE
	The program of the ITC suite were primarily designed for the semi-
	automatic analysis of forested image using the ITCVFOL & ITCISOL
	automatically delineated tree crowns, thus, the ITC bitmap (ISOLBIT)
	tends to be a dominant factor of every program. This is also generally
	true for ITCSSG, except in ManBM, ManVec, and SLayer special modes.


		TRAINSEG	Training Segments (bitmaps or vectors)
		

	Specifies a list of Training Segments (bitmap or vector layers) to be used,
	one for each species (class) signature to be created.

	EASI>TRAINSEG=n,n,n...
  
	These bitmaps may contain filled training AREAS (for uniform forest 
	stands) OR the full crown of individual trees (for mixed stands).
	These ITCs should preferably have been generated by using DCPE, 
	and thus be EXACTLY the same as the equivalent crown in ISOLBIT.
	These training areas (each in turn) will be ANDed together bitwise with
	the ISOLBIT to produce the mask which will be used to gather the MSS data
	(if at least a minimum 2x2 pixel area exist for a tree crown)

 	Pointers to ITCs to be used (e.g., an external DB of ground tree positions)
	can be used with BITBOUND in POINTS mode and EXTBIT bitmap containnig 
	pointers to the tree crown to consider. In that case, training areas
	(or full crowns) are still needed to indicate species.

	In ManVec mode, the training segments are vector layers made of individual
	tree crowns (close polygons - PCI shapes), typically delineated manually
	on the screen by an interpreter.
	The ISOLBIT and the BITBOUND parameter are disregarded.
	This is more a research mode to see if purer signatures are generated by

		SIGTYPE
		

	Specifies which type of signature is to be generated.
  	Possible types include:  MEAN/TCL/TCL2/TEXTUR/STRUCT.

	EASI>SIGTYPE="type"

	Signature Description

	MEAN:	Multispectral mean of each ITC are averaged to create
			species signature. MEAN can be used with EXTBIT to create
			LIT side MEAN and TT (tree top) MEAN signatures.
	TCL:	First eigen vector & corresponding intercept of each ITC
			are averaged to create the species signature.
	TCL2:	First eigen vector & corresponding intercept & eigenvalues
			are averaged to create species signature.
	TEXTUR:	Multispectral variance of pixels within each ITC (or LIT side))
			are averaged to create a simple species textural signature.
	STRUCT:	3D moments (now Kurtosis) of each ITC (i.e., shape)
			are averaged to create species structural signature.

	Version 2.0 introduced these all new redefined SIGTYPEs to ITCSSG.
	The user can select more than one SIGTYPE, for exemple (m=3), 
	SIGTYPE = MEAN,TEXTUR,STRUCT or SIGTYPE = MEAN+TEXTUR+STRUCT
	A covariance of appropriate size (mn*mn), describing the covariance
	of each feature selected will be created and added to the vectors.
	If the user wants other signatures, than ITCSSG is run again to  
	create other segments. (Here, n is number of channels).

       ITCMG program.  For example, say a bitmap is generated by ITCMG of type LIT,
       and specified as EXTBIT.  The bitmap contains all the pixels that form the
       lit side of the tree.  When the tree is being processed, only those pixels
       that are in the LIT mask are used in the processing of the individual tree
       signature (also used with TT or SHADE, or any other crown sub-area bitmap)

	In the BITBOUND=POINTS mode, the EXTBIT bitmap points to the tree crowns that
	should be considered.

	EASI>EXTBIT=n
	
		     BITBOUND
		

       Possible values: INC / EXC  /AUTO / CGRAV / POINTS
	(Inclusive or Exclusive or Automatic or Center_of_gravity or Pointers).

	EASI>BITBOUND="value"

       Specifies whether tree crowns that fall on the boundary of Training (testing)
	areas (TRAINSEG) should be included (INC) or excluded (EXC), or have their
	insertion decided upon automatically (AUTO) based on having 50% of their crown 
	area inside the area, or based on their "center of gravity" (stem?) being 
	inside (CGRAV) the training (testing) area.
	POINTS is a separate case in which the EXTBIT bitmap contains pointers
	to the tree crown to consider.

       Inclusive:
                   o	All crowns that have at least 2x2 pixels (and 10% of their crown)
			inside the training (testing) area are included in the output.

       Exclusive:
                   o	Crowns that are only partially in the training (testing) area
			(trees on area boundaries) are disgarded (generally).
                   o	Exception: If a tree less than 10% of its crown area
			sticking out of the testing area, it is considered IN.

	Automatic
                  o	Crowns are included in the output if more than 50% their crown
		    	area is inside the training (testing) area.

	CGRAV
                  o	Crowns are included in the output if their center of gravity
			(tree stem?) is inside the training (testing) area.

	POINTS
                  o	Crowns are included in the output if their is a pointers
			(a set pixel) in EXTBIT that points to the crown.
		   o	If this is the case, the full crown content is used
			independent of the size of the pointer.

	NOTE:	Not applicable with manual tree crowns (ManBM and ManVec).

		DETAILS
		

	ITCSSG

	**** NOT up-to-date relative to manual tree crowns (ManBM and ManVec modes).

       ITCSSG generates class signatures for different species of trees,
       specified by a set of channels to an input image, a bitmap from the ITCISOL
       program, and a series of training bitmaps.  Based on a bitmap mask formed
       by ANDing the ITCISOL and training bitmaps, a region of the image is
       scanned for trees, and a signature for the "species" is determined
       based on the data in the image.  An optional EXTBIT mask further species
       which part of each tree should be processed.  These sigatures are then written
       to a segment in the image file.  If a SDBOUT filename is specified, the
       signature information is written to a text file.


		GENERAL PROCESS
		

	Here is the general process followed by the program to generate species signatures:


	**** NOT up-to-date relative to manual tree crowns (ManBM and ManVec modes).

	The channels of the image are loaded in from the specified image file.  As well, three
	different kinds of bitmap masks are loaded in.  A bitmap mask from ITCISOL (Individual
	Tree Crown Isolation) is loaded, as well as a set of Training Masks.  The training
	masks may contain filled areas, discrete points, or filled tree crowns.  The third
	(optional) bitmap mask which may be loaded is the External Bitmap (EXTBIT).  This is
	a bitmap, usually generated by the ITCMG program which specified which parts
	of the ITCISOL bitmap should be processed in order to generate the tree signatures.
	The ITCISOL and TRAINSEG masks (each training mask and the ITCISOL mask) are ANDed
	together bitwise to form a third bitmap mask, which is the one that is used to
	determine tree positions.

	**** NOT up-to-date relative to BITBOUND

	The new mask is scanned until a tree is found.  The value of BITBOUND is considered
	here.  If INC is specified, all partial trees are considered, while EXC causes partial
	trees to be rejected.  With an "accepted" tree, the signature generator then begins
	building up the tree signature by gathering the multi-spectral information of the tree.
	For each tree a "tree node" structure is allocated.

	Basically, a tree node holds information (size, position, image values, etc.) for
	each tree and is used in the generation of signature information.  Each pixel in the
	tree is then processed, with the appropriate data from the image being stored in a
	tree node.  The External Bitmap Mask is used here to determine which information is
	kept.  If no EXTBIT is specified, then the information from all pixels contained in
	the tree are used.  If an EXTBIT value is used, only pixels that are also in the
	EXTBIT are kept for that tree.  This allows parts of the tree (for example the lit side)
	to be used, while part of it is rejected.  From the pixel (multi-spectral information)
	a mean and variance vector for the intensity values is generated and stored in the
	tree node.

	As well, an information list is created for a tree.  For each pixel in the tree, an
	information node is created which contains the actual image data (the intensity values
	of the channels) in a form more useable by the program.  All the information nodes
	together for the tree form the information list.  When an information list has been
	generated, it is processed and a correlation and covariance matrix is generated.
	Again, this information is stored in the tree node.

	When all the trees have been processed, the tree list is traversed and the signature
	information for each tree is gathered.  This information is summed and then averaged
	so that the species signature (or average tree signature) is generated.

	The results of the species signature are stored in another node called a result node.
	The values contained in the result node are then displayed and the signatures saved.

	From the covariance matrix the eigenvalues and eigenvectors are generated and also
	stored in the result node.  Once all the result nodes have been generated (one per
	species) the information is written to a PCIDSK segment (one segment per species).
	If the user has specified a segment then it is overwritten, otherwise a new segment
	is created.

	If a SDBOUT filename is specified then the species signature information is written
	to a text file.


		CLASS SIGNATURES
		

	The following information is generated for each tree in the training bitmap
	and then averaged to create the average or class (species) signatures:

       o The mean multispectral vector of all pixels contained in a tree crown.
	o The multispectral variance vector of all pixels contained in the tree crown.
	o The covariance matrix of the distribution of pixels in multispectral space
	  for each tree crown.
	o The correlation matrix of the pixels in each tree crown.
	o The eigenvalues and eigenvectors of the covariance matrix.

	The species signature may then be used to classify by the following signature
	types in ITCSC:

	Mean vector (AVG)
	The mean multispectral vector of all pixels contained in a tree crown.

	Mean vector & first principal component (MPC1)
       The "Tree Colour Line" approach in multiple dimensions - the distribution
       of pixels for each tree crown is represented by its first eigenvector
       (its colour line direction) and its mean vector (to anchor the line in
       multidimensional space).

       Mean vector & first principal component & eigenvalues (MPC1EV)
       As above (MPC1) but eigenvalues are added to describe the spread of the
       distribution in the various directions.

       Mean and covariance matrix (MCOV)
       The mean and covariance matrix of the distribution of pixels in
       multispectral space for each tree crown.



		     BITMAP MASKS AND BOUNDARIES
		

	**** NOT up-to-date relative to BITBOUND or EXTBIT

	Three different types of bitmap masks are used by ITCSSG.  The first kind is
	a bitmap mask generated by ITCISOL and specified by ISOLBIT.  This bitmap
	contains a mask of the isolated tree crowns.  This bitmap is scanned in order
	to locate a tree to be processed.

       The second kind of bitmap is a series of training bitmaps (TRAINSEG) which have
	been constructed by the user.  This can consist of a filled region (all trees
	contained in a region), filled tree crowns (an individual tree), or individual
	points (also indicating individual trees to be considered).  Each bitmap
	contains trees of one particular species.  The signatures of trees in each bitmap
	are used to create the average or species signature.  Each TRAINSEG in turn is
	ANDed together bitwise with the ISOLBIT.  This new bitmap is scanned to
	find the location of a tree.

       When the new bitmap is scanned the BITBOUND value is considered.  Possible values
       for BITBOUND include INC or EXC.  If INC is specified this indicates an "inclusive"
       border on the TRAINSEGs.  That is trees which are partially in a region (but not
       entirely) are included in the signature generation process.  If EXC is specified,
       partial trees are rejected from the species signature generation.  Generally, the
       following should be considered:

	The third type of bitmap is an External Bitmap mask specified by EXTBIT.  The
	External Bitmap Mask is used here to determine which information in a tree crown is
       kept.  If no EXTBIT is specified, then the information from all pixels contained in
       the tree are used.  If an EXTBIT value is used, only pixels that are also in the
       EXTBIT are kept for that tree.  This allows parts of the tree (for example the lit side)
       to be used, while part of it is rejected.


		     OUTPUT DATABASE STRUCTURE
		

       If a DBOUT filename is specified, then the species signature information is
       written to a text file.  The database will have the following structure for each
       entry (species signature):

	number trees-processed
       multi-spectral channel mean values
       multi-spectral channel variance values
       eigenvectors and eigenvalues
       covariance matrix

       where:
       'number' is the assigned species number
	'trees-processed' is the number of trees used in generating the species signature

       The other lines in the database refer to the signature data values.

C
C	ITCCA determines the classification accuracy of an Individual Tree Crown
C	Classification Process.  A confusion matrix is generated, based on the testing

C

Program name: 	lattops_g.cpp

Author: 	François A. Gougeon
Date:		July 2023, Nov. 2023

Description:

	Find treetops in dense areas and treetops with specific shadows in
	more open areas, as designated by the directionality mask (DIRMASK).
c
C	This program moves a window of a given size on an input image and
C	detects the local centered grey-level maximum of each window's instance.
C	For the areas covered by an input mask (DIRMASK) (e.g.: directionality
C	mask), it keeps only those max. with a significant low grey level area 
C	(i.e., a shadow) in the direction commensurate with SUNANG (180o + SUNANG).
c	(N.B.: The angle assumes North at top of the image)
c
c	Optionally: Operation under the directionality mask (open areas)
c		    are done on a smoothed version of the image, if supplied
c		    (i.e., if ILLUMCH = a,b). This may improve results.
c	This could also be a completely different channel if more useful for shadows
C
c	Optionally: If DIRMASK = 1, trees from the whole image (except under NFMASK)
c		    are considered to have discrete shadows (was SHADOW_TT) ????
C
c	Org. for full path and ArcGIS compatibility and output : basefilename_TTs.tif
c
c	*** NOTE *** Changed parameters order compared to PCI version (i.e., NFMASK before DIRMASK)
c
c	*** NOTE *** I Will not migrate TREETOPS to GDAL as LATTOPS can do it all
c			
c			
c	- NOTE:	This program (and other of my GDAL progs) always complain when overwriting an exiting 
c		output file. Most of the time it is not an issue. However, sometimes when ArcGIS has
c		control of the file, it may not overwrite at all and leave you with previous results

#### GDAL PROGRAM USAGE

> lattops_g FILE,ILLUMCH NFMASK DIRMASK WINDSIZ THRSHADE SUNANG FORTYPE TTBITM



#### GDAL PROGRAM EXAMPLES

> lattops_g PP1493386_GDAL_Tests.pix,4 - - - 50 - -

Here, the regular TREETOPS will be used throughout the image (CH4 ) using 
a 3x3 window and a shade threshold of 50.


> lattops_g PP1493386_GDAL_Tests.pix,4 386_GDAL_BM9.tif - - 50 - -

Here, the regular TREETOPS will be used throughout the image (CH4 ) using 
a 3x3 window and a shade threshold of 50. The non-forest areas (386_GDAL_BM9.tif)
will not be touched.


> lattops_g PP1493386_GDAL_Tests.tif 4 386_GDAL_BM9.tif - 5 50 - Mature 

The fouth channel of PP1493386_GDAL_Tests.tif (or .pix) is used
There is no directionality mask, thus regular TREETOP will be used throughout the image
except, under the NFMASK (386_GDAL_BM9.tif)
A 5x5 window will be used, with a shade threshold of 50.

> lattops_g PP1493386_GDAL_Tests.pix,4 BM9.tif BM10.tif 5 50 160 MAT 

The fouth channel of PP1493386_GDAL_Tests.tif (or .pix) is used
Directionality mask is BM10.tif, thus SHADOW_TT will be used throughout the image
under BM10, with a sun azimuth of 160 degrees, except, under the NFMASK (BM9.tif) 
A 5x5 window will be used, with a shade threshold (THRSHADE) of 50.
By default, shadow threshold (cause unsepcified) will be 1.3 * THRSHADE 
It could have been specified as 65, as THRSHADE=50,65 for example.



> lattops_g PP1493386_GDAL_Tests.tif,4,7 BM9.tif BM10.tif 5 50,60 160 MAT Test_TTs.tif
> lattops_g PP1493386_GDAL_Tests.tif 4,7 BM9.tif BM10.tif 5 50,60 160 MAT Test_TTs.tif

Here, a different channel (CH7) is used by the directionality analysis
and a shadow thres of 60 will be used, and an output bitmap file name is given.

SHAD_LEN - To find length of tree shadows in sparsely treed areas


Program name: 	shad_len_g.cpp
Author: 	François A. Gougeon
Date:		July 2025 (GDAL version)
Version:	1.8


Description :

This is directed at the sparse forested areas in northern Canada (e.g. NWT, Yukon)
where individual trees and their rather specific shadows are often visible.

From a bitmap showing tree shadows (often acquired by simple thresholding),
this program generates a bitmap containing some shadow length as detected within
a certain range of lengths, using lower and upper thresholds (LENG_THR in metres)
and certain range of widths (BLOB_WID in cm).

Using the above parameters, one can hopefully bypass irrelevant blobs or blobs that
are a combination of multiple shadows in the X or Y directions

It is able to report for the full image or for a certain Test Area (maybe a tif bitmap).

** MORE IMPORTANTLY **, it is able to report the average shadow length within the 
polygons (stands) of the test area (if TESTSEG is such)


Parameters :

SHAD_LEN is controlled by the following parameters:

SHAD_BM		BM-In of crude tree shadows			
SHAD_LEN	BM-Out of measured shadow lengths	
TESTSEG		Test Area Segments (BM/Vect)		
LENG_THR	Min & Max length (in metres) to include	
BLOB_WID	Min & Max blob width (in cm) to include	
SUNANG		Sun azimuth and elevation		

Program Usage :

> shad_len_g SHAD_BM SHAD_LEN TESTSEG LENG_THR(m) BLOB_WID(cm) SUNANG
	  
> shad_len_g Input_BM.tif Out_Bitmap.tif - 2,15 50,400 - 		// does FULL image (SUNANG at 180,45)

> shad_len_g PP784481_Shadows.tif PP784481_Length.tif Test_Area.tif  - - - -

> shad_len_g PP784481_Shadows.tif PP784481_Length.tif PP784481_Segm26.shp  - - - -


Notes :

The original shadow bitmap, if obtained by simple thresholding, should try to avoid
water bodies and large shaded areas (e.g., darken mountain sides).

The intent here, is to infer tree heights from shadow lengths. With a sun elevation of
about 45 degrees in Canada's Northern areas, shadow lengths could correspond to 
tree heights.

Info about shadow lengths in a given area (a stand) could provide info about 
whether we are dealing with mature trees or regeneration or severely stunted trees.
This could direct the use of MATURE vs REGEN flag in program like LATTOPS.

Given the image acquisition location, date, and time, you can get the sun'azimuth 
and elevation from the NOAA Apps (or other) at :

https://gml.noaa.gov/grad/solcalc/azel.html

This is required to get proper tree heights from their specific shadows.

If not known (i.e., no image acquisition info), sun azimuth can be measured on
the image looking at shadows (with a reporter or guessing) and 45 degree elevation
can be used (typical of such northern latitude) 

Importantly, sun azimuth is used by SHAD_LEN to look for shadows in the proper direction,
thus maximizing the chances of getting the end point (corresponding the tree tree top)
